# Call Transfer Graph Loop Analysis

Published October 12, 2026.

## Research question

Call Transfer Graph Loop Analysis asks which routing paths create repeated transfers without accepted ownership. The unit of analysis, observation window, eligible population, exclusions, and intended operational decision must be registered before outcomes are inspected. The study reports evidence for a bounded call workflow; it does not certify a vendor, infer caller intent, or establish a universal performance benchmark.

## Freeze the population and rule versions

In stage 1 of Call Transfer Graph Loop Analysis, retain source queue, destination queue, hop sequence, acceptance event, fallback, caller exit, and final owner. Link events with stable call and workflow identifiers rather than names or approximate timestamps. Preserve original timezones and source values, then add normalized fields separately. Report eligible, observed, excluded, unavailable, late, conflicting, and unresolved records as separate counts. This prevents a clean subset from silently representing the difficult calls most relevant to which routing paths create repeated transfers without accepted ownership.

Stage 1 of Call Transfer Graph Loop Analysis, freeze the population and rule versions, uses a predeclared classification guide and a second reviewer for a planned subset. Reviewers work independently before adjudication and record why competing classifications were rejected. Segment results by workflow version, queue, channel, shift, language or network condition only when that comparison was specified and sufficiently populated. Do not copy customer profiles or credentials into an analysis file. Publish denominators and uncertainty, not worker rankings from small samples.
